# Phase 999.1: Stadia Controller Support - Context

**Gathered:** 2026-05-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Add the Google Stadia controller as a second supported input device. The Stadia controller maps to the same viewport navigation commands already used for Xbox (walk, orbit, pan, zoom, button mappings). This phase delivers hardware support only — no new navigation features or Stadia-exclusive bindings.

</domain>

<decisions>
## Implementation Decisions

### Input Layer
- **D-01:** Use the **ViGEm Bus Driver** approach. The user (or end user) installs the free open-source ViGEm Bus Driver, which re-exposes the Stadia HID device as a standard XInput controller. No changes to `XInputDotNetPure` or `GamePad.GetState()` — Stadia becomes indistinguishable from Xbox at the XInput layer.
- **D-02:** If a Stadia controller is detected as a raw HID device (not yet mapped via ViGEm), show a **one-time dialog** with an install link: "Stadia controller detected — install ViGEm Bus Driver to enable it." Detection uses Windows HID device enumeration by VID/PID.

### Button Naming in UI
- **D-03:** Keep **Xbox labels** in all settings and mapping UI. Since ViGEm makes Stadia appear as an XInput device with identical A/B/X/Y/LB/RB/LT/RT layout, no label changes are needed. No controller-detection logic added to the UI layer.

### Multi-Controller Coexistence
- **D-04:** **First connected wins** — CtrlWiz uses XInput player index 0. Whichever controller occupies that slot (Xbox or Stadia via ViGEm) drives navigation. No UI change needed. User can manage slot assignment at the OS/driver level.

### Abstraction Scope
- **D-05:** **Leave `XInputDotNetPure` untouched.** No rename, no interface abstraction. The only new code is HID detection for the ViGEm dialog. A future `IGamepadProvider` abstraction (if ever needed) is its own separate phase.

### Claude's Discretion
- ViGEm download link to use in the dialog — use the official GitHub releases page for `ViGEm/ViGEmBus`
- HID detection implementation detail (WMI vs. SetupAPI vs. `System.Management`) — choose whichever is simplest in .NET 4.8

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `XInputDotNetPure.GamePad.GetState()` — unchanged; Stadia via ViGEm uses this exact call
- Existing dialog/message infrastructure in `CtrlWizNW` — reuse for the ViGEm install prompt
- `CtrlWizNW.log` file logger in `%TEMP%` — log HID detection events here

### Established Patterns
- P/Invoke for Windows API calls — the codebase already uses this pattern (xinput1_4.dll); HID enumeration can follow the same pattern
- .NET Framework 4.8 — no WinRT, no .NET 6+ APIs; use `System.Management` or SetupAPI P/Invoke for device enumeration

### Integration Points
- `CmdViewpoint.cs` — navigation loop; calls `GamePad.GetState()` — **no changes needed** with ViGEm approach
- Plugin startup path — the HID detection + dialog should fire at activation time, not on every poll

</code_context>

<specifics>
## Specific Ideas

- The ViGEm dialog should fire once per session when a non-XInput HID gamepad is detected at activation, not on repeat polls
- The dialog should include a direct download link to the ViGEm GitHub releases page

</specifics>

<deferred>
## Deferred Ideas

- **IGamepadProvider abstraction layer** — Refactor `XInputDotNetPure` into a controller-agnostic interface. Discussed and explicitly deferred; would be its own phase if ever prioritized.
- **Stadia-specific button labels in UI** — Auto-detecting controller type and swapping label language. Deferred as unnecessary complexity given ViGEm's transparent XInput remapping.
- **User-selectable controller slot** — Allowing users to pick XInput player index 1–4 in settings. Deferred; first-connected-wins is sufficient for now.

</deferred>
