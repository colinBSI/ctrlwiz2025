## Summary

This phase adds a lightweight Stadia controller detection path to the existing CtrlWiz NW plugin. Because ViGEm Bus Driver (D-01) makes the Stadia controller appear as a standard XInput device, the entire navigation stack (`GamePad.GetState()`, `XInputDotNetPure`, `CmdViewpoint.cs` poll loop) remains untouched. The only new code is: (1) a HID scan at plugin activation time, and (2) a one-time `MessageBox`-based dialog if the Stadia VID/PID is found but ViGEm is not installed.

The simplest .NET 4.8-compatible HID detection approach is `System.Management` (WMI) querying `Win32_PnPEntity` by `DeviceID` string containing `VID_18D1&PID_9400`. `System.Management.dll` is already part of the .NET Framework — no NuGet package is needed. The dialog pattern is `System.Windows.Forms.MessageBox.Show` with a "Yes/No" or "OK" button plus a `Process.Start(url)` call — both patterns are already used throughout the codebase.

The one-time suppression needs a persisted flag (`bool` user setting). The existing `CtrlWizNW.UI\Properties\Settings.settings` / `Settings.Designer.cs` pattern using `ApplicationSettingsBase` (`UserScopedSetting`) is the established mechanism to add it without any new infrastructure.

**Primary recommendation:** New class `StadiaDetector` in `CtrlWizNW` project; called once from `ExecuteCommand` before the license/activation flow; persisted flag in `CtrlWizNW.UI` Settings.

### Pattern 1: WMI HID VID/PID Scan

**What:** Query `Win32_PnPEntity` for any device whose `DeviceID` contains the Stadia VID/PID string.
**When to use:** Once per session at plugin activation, not in the poll loop.

```csharp
// Source: System.Management / WMI Win32_PnPEntity documentation
// VID 0x18D1 = Google Inc., PID 0x9400 = Stadia Controller (USB HID mode)
// [VERIFIED: WebSearch cross-referenced against Chrome WebHID blog + github.com/walkco/stadia-vigem]

using System.Management;

internal static class StadiaDetector
{
    private const string StadiaVidPid = "VID_18D1&PID_9400";
    private const string ViGEmReleasesUrl = "https://github.com/nefarius/ViGEmBus/releases";

    /// <summary>
    /// Returns true if a device with the Stadia VID/PID is present in the HID tree.
    /// Uses WMI Win32_PnPEntity — runs in ~10-50 ms, acceptable for activation-time call.
    /// </summary>
    public static bool IsStadiaPresent()
    {
        try
        {
            using (var searcher = new ManagementObjectSearcher(
                "SELECT DeviceID FROM Win32_PnPEntity WHERE DeviceID LIKE '%" + StadiaVidPid + "%'"))
            {
                foreach (ManagementObject obj in searcher.Get())
                {
                    obj.Dispose();
                    return true;
                }
            }
        }
        catch { /* WMI unavailable — silent fail, no detection */ }
        return false;
    }

    /// <summary>
    /// Call once at plugin activation. Shows a one-time dialog if Stadia is present
    /// but ViGEm has not yet been installed (ViGEm presence is inferred from whether
    /// the Stadia device ALSO appears as an XInput device — simplification: just show
    /// once and let user decide).
    /// </summary>
    public static void CheckAndNotify()
    {
        if (!IsStadiaPresent())
            return;

        if (CtrlWiz.NW.UI.Properties.Settings.Default.StadiaViGEmDialogShown)
            return;

        var result = System.Windows.Forms.MessageBox.Show(
            "A Google Stadia controller was detected.\n\n" +
            "To use it with CtrlWiz, install the free ViGEm Bus Driver, which re-exposes\n" +
            "the Stadia controller as a standard Xbox controller.\n\n" +
            "Open the ViGEm download page now?",
            "Stadia Controller Detected",
            System.Windows.Forms.MessageBoxButtons.YesNo,
            System.Windows.Forms.MessageBoxIcon.Information);

        if (result == System.Windows.Forms.DialogResult.Yes)
        {
            try { System.Diagnostics.Process.Start(ViGEmReleasesUrl); }
            catch { /* browser launch failed — non-fatal */ }
        }

        CtrlWiz.NW.UI.Properties.Settings.Default.StadiaViGEmDialogShown = true;
        CtrlWiz.NW.UI.Properties.Settings.Default.Save();
    }
}
```

### Anti-Patterns to Avoid

- **Calling WMI in the poll loop:** `Update()` runs continuously; WMI queries take 10-50 ms — would destroy frame rate. Detection fires once at `ExecuteCommand`, not in `Update()`.
- **Detecting ViGEm installation by querying a separate driver VID/PID:** Adds complexity; the one-time dialog approach (show once, user decides) is sufficient per D-02.
- **Adding new NuGet package for HID:** `System.Management` is inbox; no new dependencies needed.
- **Modifying `XInputDotNetPure`:** Explicitly locked out by D-05.
- **Adding Stadia-specific UI labels:** Explicitly locked out by D-03.

## Hardware Facts: Stadia VID/PID

| Mode | VID | PID | Notes |
|------|-----|-----|-------|
| USB HID (wired) | `0x18D1` (Google Inc.) | `0x9400` | The mode relevant to this phase — Stadia plugged in via USB-C |
| Bluetooth | `0x18D1` | Possibly same `0x9400` or variant | BT mode was enabled via firmware update post-service-shutdown; no confirmed different PID found in research |

**Detection string:** `VID_18D1&PID_9400` — this substring appears in `Win32_PnPEntity.DeviceID` for the wired USB HID mode. [VERIFIED: WebSearch — Chrome WebHID blog states productId=37888=0x9400 and vendorId=6353=0x18D1; corroborated by github.com/walkco/stadia-vigem]

**BT mode caveat:** [ASSUMED] Bluetooth-connected Stadia controllers may enumerate with the same or a different PID on Windows. Since the primary use case is USB (most gaming setups), and since ViGEm works with USB-connected Stadia, the single PID `0x9400` is sufficient for MVP. If the BT PID differs, the WMI query can be extended with an OR clause.

## Common Pitfalls

### Pitfall 1: WMI Query Performance in Poll Loop
**What goes wrong:** Developer places `IsStadiaPresent()` inside `Update()` (the async navigation loop). WMI queries take 10-100 ms — destroys frame rate.
**Why it happens:** It looks logical to check device presence continuously.
**How to avoid:** Call `StadiaDetector.CheckAndNotify()` exactly once, in `ExecuteCommand()`, before `Button1()` is invoked.
**Warning signs:** Navigation becomes sluggish after controller detection code is added.

### Pitfall 2: Settings.Designer.cs Hand-Edit Drift
**What goes wrong:** `Settings.settings` XML and `Settings.Designer.cs` get out of sync — setting exists in XML but not in the generated class (or vice versa).
**Why it happens:** Hand-editing both files instead of using the VS settings designer.
**How to avoid:** Add the setting via Visual Studio's Settings Designer (Project > Properties > Settings tab) which regenerates both files atomically; or carefully hand-edit both following the existing pattern exactly.
**Warning signs:** `Settings.Default.StadiaViGEmDialogShown` throws a NullReferenceException at runtime.

### Pitfall 3: System.Management Reference Missing
**What goes wrong:** `System.Management` is available in the .NET Framework GAC but must be explicitly referenced in the project — it is NOT included by default in `CtrlWizNW.csproj`.
**Why it happens:** `System.Management` is a separate assembly (`System.Management.dll`) even though it is inbox.
**How to avoid:** Add a reference to `System.Management` in `CtrlWizNW.csproj` (Add Reference > Assemblies > Framework > System.Management). No NuGet install needed.
**Warning signs:** `CS0246: The type or namespace name 'ManagementObjectSearcher' could not be found`.

### Pitfall 4: WMI Query String Case Sensitivity
**What goes wrong:** WQL LIKE operator is case-insensitive in practice, but `DeviceID` string format varies: some entries use `VID_18D1&PID_9400`, others `VID_18d1&pid_9400`.
**Why it happens:** Windows device manager normalizes to uppercase, but WMI results can differ across Windows versions.
**How to avoid:** Use the uppercase form `VID_18D1&PID_9400` in the LIKE clause — this is the documented Windows format. [ASSUMED — WMI LIKE clause behavior across Win10/11 versions not exhaustively tested]

### Pitfall 5: Dialog on Background Thread
**What goes wrong:** If `CheckAndNotify()` is ever called from a background thread (e.g., if detection is moved into a Task), `MessageBox.Show` will still appear but may not be parented to the NW main window, causing focus issues.
**Why it happens:** WinForms dialogs need to run on the UI thread.
**How to avoid:** Keep `CheckAndNotify()` called directly from `ExecuteCommand()`, which runs on the NW UI thread.

## Open Questions (RESOLVED)

1. **Stadia Bluetooth PID on Windows**
   - RESOLVED: Use `0x9400` for USB HID MVP. If BT PID differs, extend with OR clause on user report.
   - What we know: USB HID PID is confirmed `0x9400`. BT firmware was released post-shutdown.
   - What's unclear: Whether Windows enumerates BT-connected Stadia with same PID or a different one.
   - Recommendation: Use `0x9400` for MVP. Add a user-reported issue channel note in the dialog if BT detection is needed later.

2. **Should the dialog fire once ever, or once per NW session?**
   - RESOLVED: Persist permanently (`UserScopedSetting`). Once the user has been told, they know.
   - What we know: CONTEXT.md says "once per session" for the dialog trigger, but "once" (persisted) for suppression.
   - What's unclear: After user installs ViGEm, should the dialog ever reappear? (e.g., after ViGEm uninstall)
   - Recommendation: Persist the flag permanently (`UserScopedSetting` persists across sessions). Once the user has been told, they know. If ViGEm is later uninstalled, the Stadia controller simply won't function as XInput — no need to re-prompt.
